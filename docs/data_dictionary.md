# Data Dictionary

## Synthetic overdraft-risk training dataset (`data/synth/risk.parquet`)

### Dataset overview
`data/synth/risk.parquet` captures the feature matrix that powers `predict_overdraft_risk`. Each row is generated by `python -m cashsim.ml.synth` (see DVC stage `risk_synth` in `dvc.yaml`) and mirrors the inputs the simulator would see for a synthetic household over the next 30 days. Metadata about the run (seed, start date, horizon, feature list, label name, row count) lives alongside it at `artifacts/risk/synth_meta.json`.

### Purpose and primary use cases
- Train and evaluate the static risk models (`logreg`, `gbdt`) that the CLI/Streamlit UI exposes via `cashsim.risk.predict_overdraft_risk`.
- Exercising the downstream evaluation stack (`cashsim.ml.evaluate`) so metrics/plots remain reproducible and auditable.
- Serving as a synthetic proxy while wiring up future real-data ingest without depending on customer data.

### Source systems
- **CashSim synthetic risk generator** (`python -m cashsim.ml.synth`), which pulls `Dials` inputs, runs `simulate_month`, and featurizes the results via `cashsim.ml.features.FEATURE_COLUMNS`.
- **DVC stage `risk_synth`** (see `dvc.yaml`/`dvc.lock`), ensuring the dataset is reproducible and tied to the code/params that produced it.

### Owner and point of contact
- Owner: CashSim project (`https://github.com/josuejero/cashsim`). Report data issues by opening a GitHub issue in this repo so maintainers can trace the offending commit/params.

### Grain
- One synthetic scenario aggregated over the configured horizon (default 30 days).

### What 1 row represents
- A single simulated household’s view of cash flow, debts, bills, and ancillary data (gas, one-offs) over the next horizon. The row includes explainable features and a binary label indicating whether any day in the simulation had a negative balance.

### Primary keys and uniqueness expectations
- There are no natural keys; each row is one independent draw from the synthetic generator. Duplicates are acceptable because the model benefits from iid samples. Audits should verify `len(df)` matches `artifacts/risk/synth_meta.json["n"]`.

### Update cadence
- Manual. Re-run `dvc repro risk_synth` or `python -m cashsim.ml.synth --out data/synth/risk.parquet --meta artifacts/risk/synth_meta.json` whenever the generation logic (`src/cashsim/ml/synth.py`, `src/cashsim/sim/core.py`, `src/cashsim/models.py`) or the risk params (`params.yaml`) change. CI runs this before training/eval stages.

### Refresh schedule (hourly/daily/weekly)
- Not scheduled. Refreshes occur on demand prior to training, demo validation, or whenever new assumptions need to be captured.

### Late-arriving data behavior
- N/A. The dataset is regenerated in full; backfilling is accomplished by rerunning the generator with the desired `start_date`/`horizon_days` rather than appending incremental rows.

### “Freshness” expectations
- Treat the dataset as stale if the generator code, parameters, or `params.yaml` defaults differ from the last run. When updating the model, always re-run `risk_synth` so downstream evaluation uses fresh rows that match the latest assumptions.

### Field definitions (the main table)

| Column | Type | Required? | Definition | Allowed values or valid range | Example values | Notes (edge cases) |
| --- | --- | --- | --- | --- | --- | --- |
| `starting_balance` | `float64` | Y | Cash-on-hand at horizon start (`Dials.current_cash`). | 0.00–≈2,500.00 (uniform random). | `1544.38` | Rounded to 2 decimals; 0 indicates a fully drained wallet. |
| `safety_cushion` | `float64` | Y | Extra buffer CashSim holds before paying expenses (`Dials.safety_cushion`). | 0.00–1,500.00 | `799.90` | Helps the reserve calculations; zero when households run lean. |
| `weekday_earnings` | `float64` | Y | Daily earning assumption applied 7 days/week. | 0.00–300.00 | `109.75` | Constant across the horizon, so it masks weekday/weekend variability. |
| `total_monthly_bills` | `float64` | Y | Sum of bill amounts due in the horizon (0–5 bills). | 0.00–4,500.00 | `694.32` | Zero if no bills exist; derived from Bill.amount. |
| `total_debt_balance` | `float64` | Y | Total outstanding balance across credit cards and IOUs. | 0.00–32,000.00 (3 CC × 8k + 2 IOU × 4k) | `12,325.94` | Increases with new credit/IOU entries added to `Dials`. |
| `total_debt_minimum` | `float64` | Y | Sum of minimum payments (max of floor vs. pct) owed on credit cards + IOUs. | ≥0.00 | `456.76` | Fluctuates with APR payment rules; floors (15–50) can dominate on low balances. |
| `oneoff_total_horizon` | `float64` | Y | Sum of scheduled one-off expenses whose due dates fall inside the horizon. | 0.00–6,000.00 (4 × 1,500) | `1,672.04` | One-offs are prioritized by `priority`; zero when no entries exist. |
| `gas_pct` | `float64` | Y | Fraction of daily earnings reserved for gas-related spend. | 0.05–0.25 | `0.167` | Used by `apply_gas_skim_and_fillups`; non-zero gas bucket only when earnings > 0. |
| `gas_fill_size` | `float64` | Y | Target fill-up amount the gas bucket tries to accumulate before purchases. | 10.00–70.00 | `19.94` | Ignores actual miles; a heuristic tied to `gas_pct`. |
| `num_bills` | `float64` | Y | Count of monthly bills (`len(dials.bills)`). | 0.0–5.0 | `2.0` | Stored as float to stay compatible with the ML pipeline; always an integer value. |
| `num_debts` | `float64` | Y | Count of credit cards + IOUs. | 0.0–5.0 | `4.0` | Records how many debt instruments contribute to `total_debt_balance`. |
| `num_oneoffs` | `float64` | Y | Count of one-off obligations. | 0.0–4.0 | `4.0` | Zero when no extra one-off is scheduled. |
| `label_overdraft` | `float64` | Y | Binary label (1.0 if any day in `simulate_month` went below zero, else 0.0). | `{0.0, 1.0}` | `0.0` | Target for classifiers; convert to `int` or `bool` before logging metrics. |

### Metric definitions (if you compute KPIs)

| Metric name | Formula | Grain | Known biases or caveats | Recommended interpretation |
| --- | --- | --- | --- | --- |
| `auc` | `roc_auc_score(y_true, y_pred_proba)` | Per evaluation run (dataset-level). | Synthetic labels lack real noise, so AUC may be overly optimistic. | Measures ranking power: higher is better for separating overdraft vs. safe samples. |
| `brier` | `brier_score_loss(y_true, y_pred_proba)` | Per evaluation run. | Sensitive to class imbalance (≈40% positives in current sample). | Lower values mean probabilities align with outcomes; target calibration. |
| `calibration_by_bin` | `sklearn.calibration_curve(..., n_bins=10)` → `(mean_pred, frac_pos)` pairs | Quantile bins (10 bins default). | Bins depend on predicted quantiles; noisier in extremes with few examples. | Trace how well predicted probabilities match observed defaults; goal is to stay near the diagonal. |

### Common data quality failure modes you’ve seen
- Forgetting to run `dvc repro risk_synth` after editing `src/cashsim/ml/synth.py` or `params.yaml`, which leaves `data/synth/risk.parquet` stale and misaligned with the code being evaluated/train.
- Adding or removing features in `FEATURE_COLUMNS` without regenerating the Parquet file, resulting in `sklearn` pipelines reading the wrong order of columns.
- `label_overdraft` becoming constant (all 0s or 1s) when the simulation horizon never strays below zero (e.g., `weekday_earnings` ≫ obligations), which makes metrics like AUC undefined.

#### Fields that are unreliable under certain conditions
- `weekday_earnings` assumes a 7-day-a-week cadence and hides weekday/weekend variation; real pay schedules might require external normalization.
- `gas_pct` and `gas_fill_size` are heuristic knobs; when `weekday_earnings` is zero or near zero, the gas bucket spends whatever remainder exists and the feature loses interpretation.
- `oneoff_total_horizon` jumps discretely when `horizon_days` grows; comparing versions generated with different horizons requires normalizing to the horizon length.

#### Any intentional exceptions (example: “unknown” values)
- All counts (`num_*`) and the label are stored as floats to minimize schema churn when feeding into scikit-learn pipelines, even though they represent integer/binary concepts.
- There are no `null` values by design; if nulls appear, they signal that upstream serialization (Parquet write) or feature generation broke unexpectedly.

### Data quality rules summary
- **Missingness (required fields)**: Assert that `.isnull().any()` is `False` for every column; the generator never emits `NaN`s.
- **Uniqueness (keys)**: Not enforced—treat the dataset as a bag of iid samples. Verify row count matches metadata instead of dedup checks.
- **Validity (ranges/allowed values)**: Enforce ranges (e.g., `starting_balance ≥ 0`, `gas_pct ≤ 1`, `label_overdraft ∈ {0,1}`) via unit tests or simple asserts before training.
- **Relationships (FK coverage)**: Not applicable; the dataset is intentionally flat with no inbound/outbound foreign keys.
